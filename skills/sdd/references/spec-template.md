# SDD spec 단일 문서 템플릿

새 SDD 사이클은 spec·설계·context를 `docs/sdd/spec/{YYYY-MM-DD}-{feature}.md` 한 문서에 담는다.
task 문서와 `ORCHESTRATOR_STATE.md`는 별도로 둔다. 아래 골격의 섹션 제목과 순서를 유지한다.
`## 기능 지도`, `## UI`, `## 구현 계획`은 조건부 섹션이다.

## 가정

- 인터뷰에서 합의한 가정. 근거가 없으면 "추론"으로 표기한다.

## 코드 조사

- 기존 코드의 사실을 근거(파일:라인, 커밋, PR)와 함께 적는다. 근거가 없으면 "추론" 또는 "모름".
- 호출관계·영향 범위·구현 걸림돌 요약. 코드맵 원본은 붙이지 않는다.

## 제약

Change:
- 이번에 바꾸는 것

Avoid:
- 하지 말아야 할 접근

Risk:
- R1. 위험과 대응

## UI

(조건부: 이미 나온 디자인이 있을 때만. 링크만 적고 화면 구성을 새로 설계하지 않는다.)

## 설계 결정

- D1. 합의된 선택과 근거. 새 구조·알고리즘 설계는 여기에 쓰지 않는다.

## 테스트 전략

- 테스트 seam, 테스트 타입, 수동 검증 항목.
- UI를 포함하는 변경이면 개발자가 직접 확인할 수동 테스트 시나리오를 result 문서에 기록한다. E2E는 수동 확인 후 요청이 있을 때만 작성한다.

## 적용 규칙

- 로드된 규칙(CLAUDE.md 등) 중 이번 변경에 걸리는 것만 적는다. 경로를 하드코딩하지 않는다.

## 빌드·테스트 명령

- 복사하지 않는다. 프로젝트 루트 `CLAUDE.md`(없으면 `CLAUDE.local.md`)의 빌드/테스트 절을 따른다.
- 구조·스타일도 같은 방식으로 링크로 대체한다.
