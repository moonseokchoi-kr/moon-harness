# why — 코드의 동기·의도 조사

코드는 **무엇을 하는지**만 보여주고 **왜 존재하는지**는 커밋·PR·티켓·문서·대화에 흩어져 있다. 이 스킬은 그 흔적을 모아 출처와 함께 답하고, 근거가 없으면 없다고 말한다. 추측을 사실처럼 쓰지 않는 것이 핵심이다.

## 읽기 전용 규칙 (프롬프트 규칙)

조사 중에는 **읽기·조회만** 한다.

- 금지: 파일 쓰기·수정·삭제, 커밋, 브랜치 변경, 티켓/PR/문서/채팅에 대한 생성·수정·댓글·전송 등 **외부 시스템** 변경.
- 이는 **프롬프트 규칙**이다. 훅이나 권한으로 강제되지 않으므로 서브에이전트에 조사를 맡길 때도 프롬프트에 그대로 전달한다.
- 조사 결과는 대화로만 보고한다. 문서로 저장하려면 사용자가 별도로 요청해야 한다.

## 절차

### Step 1 — 대상과 질문 확정

대상(코드 조각, 패턴, 기능, 설계 결정)과 질문(근거, 트레이드오프, 외부 제약, 죽은 코드 여부)을 정한다. 대상이 모호하면 열린 파일·최근 대화에서 가장 그럴듯한 해석을 한 줄로 밝히고 진행한다.

### Step 2 — 코드 앵커 확보

조사 전에 직접 실행해 시드 컨텍스트를 만든다.

- `git blame -L <시작>,<끝> <파일>` — 마지막으로 건드린 커밋
- `git log --follow -p -- <파일>` / `git log --oneline -20 -- <파일>` — 이름 변경을 넘어선 이력, 제목의 PR 번호 `(#1234)`
- `gh pr view <번호> --json title,body,author,mergedAt,closingIssuesReferences,comments,reviews` — 실질적인 커밋의 PR 본문·리뷰
- 코드 주석, 함께 추가된 테스트, 연결된 티켓 ID

세부 명령과 함정은 `references/source-control.md`.

### Step 3 — 다른 근거 카테고리 조사

사용 가능한 MCP를 확인해 카테고리(이슈 트래커, 장문 문서, 팀 채팅, 관측·에러 추적 등)에 매핑한다. 범위가 넓으면 Explore 서브에이전트(`subagent_type: "Explore"`)에 카테고리별 조사를 병렬로 맡기되, 코드 앵커와 위의 읽기 전용 규칙을 프롬프트에 넣는다. 카테고리별 확인 요령은 `references/context-sources.md`.

- 해당 카테고리의 **MCP가 없으면 한 줄로 남긴다**: "팀 채팅: MCP 없음, 조사 누락."
- 검색했는데 아무것도 없으면 무엇을 어떻게 검색했는지와 함께 "없음"으로 기록한다. 건너뛴 이유는 반드시 적는다.

### Step 4 — 사실 / 추론 / 모름 분리

모든 주장은 한 구역에 속한다. 기준과 표현법은 `references/epistemics.md`.

- **사실**: 작성자가 직접 쓴 문장(PR 본문, 티켓, 주석)으로 인용 가능한 것
- **추론**: 정황으로 도출한 해석. 근거 사슬을 드러내고 단정하지 않는다
- **모름**: 찾아봤지만 확인하지 못한 것. 검색 범위를 구체적으로 적는다

가장 최근 커밋이 곧 의도라고 가정하지 않는다. 현재 모양은 여러 결정이 쌓인 결과일 수 있다.

### Step 5 — 보고

1. 질문과 대상
2. 사실 (인용·출처 포함)
3. 추론 (근거 사슬 포함)
4. 모름 + 조사 누락 카테고리
5. 조사한 출처 목록 (빈 결과·건너뛴 것 포함, 한 줄씩)

사용자가 이 코드를 바꾸려는 맥락이면 마지막에 계보 결과를 변경 제약으로 변환한다.

- **Preserve**: 근거가 확인된 유지 대상 (동작, 계약, 가드)
- **Change**: 안전하게 바꿔도 되는 부분과 그 이유
- **Avoid**: 과거에 시도했다가 되돌려졌거나 근거상 피해야 할 방향
- **Risk**: 근거가 부족해 바꿀 때 확인이 필요한 지점 (모름 항목에서 도출)

## 비목표

- 런타임 동작 설명(how)은 다루지 않는다.
- 산출물을 저장하거나 다른 단계의 게이트로 쓰지 않는다. 대화용 컨텍스트다.
